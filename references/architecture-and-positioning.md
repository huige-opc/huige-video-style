# 技能结构与定位（2026-11-23 讨论整理）

这份文档回答三类问题：目录到底谁是谁、模板为什么分大小写、这个技能到底该当剪辑还是当生成用。以后忘了先看这里。

## 1 · 两棵树：`template/` 和 `templates/`

```
skills/huige-video-style/
  engine/           引擎（场景、人物窗、字幕、渲染）
  template/         给人用的源码与示范（单数）
    section/        空白分镜骨架：index.html + scenes.js
    demo/           t01–t23：同一段 15 秒自我介绍的 21 种风格示范
    sample5/        t24、t24-layouts、t26、t27：后出模板的短样片
    concepts/       t30–t200：162 套 10 秒概念模板（可复制改写）
    examples/       本机验收片的 4 段实现（T159/T139/T158/T106）
  templates/        给机器用的安装包（复数）
    T01/1.0.0/ … T27/1.0.0/   共 23 套
      template.json  元数据：ID、画幅、能力、依赖、源码指针
      SKILL.md       给 Core 的使用说明
      runtime/       auto-skin.js、scenes.js、index.html
      config/        skin.json、defaults.json
      assets/        manifest.json
      checksums.sha256
```

| | `template/`（单数） | `templates/`（复数） |
|---|---|---|
| 给谁 | 人：学习、复制、手写 | 机器：HUIGE-Core Registry |
| 内容 | 真正的 `index.html` + `scenes.js` | 元数据 + 自动适配器 + 打包后的 runtime |
| 能否直接出片 | 能，满血 | 只借窗口/配色/版式，草稿级 |
| 能否随便改 | 能，就是源码 | 不要改，改了校验/版本对不上 |

关系：`templates/T01/1.0.0/template.json` 的 `sources.manual_scene` 指向 `template/demo/t01/scenes.js`；
小写是源码，大写是发布包。

## 2 · 大写 T 和小写 t 的区别

- **小写 `t01`**：目录约定，出现在 `template/demo/`、`template/sample5/`，给人看和改。
- **大写 `T01`**：模板 ID，出现在 `templates/`，给 Core 安装和调用。
- 两边**不是同一个文件**：小写 demo 依赖 `intro.js` 的 15 秒共享时间轴；大写包里的 `runtime/scenes.js` 去掉了共享依赖、自己写时间轴和媒体路径，有的还加了 16:9/9:16 适配。可以直接比 md5，不一样。
- 开发者流程：改小写 → 泛化 → 补 `template.json`/`skin.json`/`checksums` → 写 `auto-skin.js` → 打包成 `Txx-1.0.0.zip`。小写改好不会自动变成大写包。

## 3 · demo / sample5 / concepts / examples 的区别

| 目录 | 批次 | 共用时间轴 | 用途 |
|---|---|---|---|
| `demo/` | 第一批 T01–T23 | `intro.js`，15 秒自我介绍 | 同一段话横评 21 种风格，挑模板 |
| `sample5/` | 后出 T24/T26/T27 | `sample.js`，5 秒素材 | 后出模板的短样片；T26 是 9 版式×1.6s（14.4s），T27 是 5s 视频墙 |
| `concepts/` | 补充的 T30–T200 | 各自 10 秒三场 | 可直接复制成项目分镜的素材库 |
| `examples/` | 本机实战沉淀 | 各自真实时长 | 已验收的 4 段，教怎么把概念模板改成 N 秒 |

样本覆盖审计（2026-11-23）：23 个大写包中，20 套有 `template/demo/tNN`，T24/T26/T27 在 `sample5/`，每套都有样本；
T08 只有小写 demo、没有大写包（现成缺口）。T26/T27 的样片代码来自各自 package 的 `runtime/`，不是另写。

## 4 · 模板到底是什么

一句话：**模板 = 一套固定的视觉变量 + 组件词汇 + 组合规则 + 适用题型。**

换风格本质是换这七类东西：
1. 背景/纹理/装饰；
2. 色彩系统（主色、强调色、文字色、对比关系）；
3. 字体系统（字族、字号层级、字重、字距、行距）；
4. 版式网格（安全区、分栏、卡片形状、留白、对齐）；
5. 动效与转场（入场、持续微动、转场、相机）；
6. 人物窗（位置、形状、缩放、描边、阴影）；
7. 组件词汇（卡片、标签、图标、箭头、印章、贴纸、图表）。

但模板不是纯皮肤，还带“适用题型”：开场、对比、流程、数据、情绪、收尾。选模板先看它适合讲什么，再看颜色。

## 5 · 两条产品线：剪辑 vs 生成

| | 剪辑包装（当前主线） | 生成视频 |
|---|---|---|
| 主体 | 人物与表演 | 脚本与图形 |
| 素材 | 必须有原始口播/演示 | 声音 + 时间文本即可，人物可占位/卡通 |
| 模板作用 | 字幕、节奏、少量图形叠加 | 整屏画面由模板生成 |
| 人物占比 | 应高：全幅/中近景为主 | 可以小窗甚至无人物 |
| 依赖 | 模板语法 + 分镜编排 | 内容槽位 + planner + adapter |

结论：同一个内核和资产库能长出两条线，但**模板类型不能互相替代**。继续加剪辑型模板（金句卡、logo、结尾卡）只会让剪辑更强，
不会让生成变好；生成需要带内容槽位、长叙事结构、可编排的章节级模板。

## 6 · 人物占比问题（暂不改，后续再动）

现象：产物里人物总是缩在方框/圆框，全幅几乎没有。
真实原因（按权重）：
1. 窗口大小和位置是模板里的 `C.huigeKeys` 写死的，默认就小；
2. 人物在窗口里也小：原片偏远景时 `C.face.h` 占比低，引擎又用 `headFill` 封顶，头最多占窗口 60%；
3. 自动适配器保守，几乎全程小窗；手写时也常把腾出的区域留空。

技能里**没有景别识别**：`engine.js` 只有 `C.face` 与 `headFill`，`HUIGE-Core/core/face.py` 只做人脸标定，都不判断远景/中近景。
所以纯口播近景也不会自动全幅。

后续改法（真人出镜、需要突出人物时）：
- 加景别模块：用 `C.face.h` 占画面高度比例 + 头顶留白，输出“可全幅 / 可大卡 / 只适合小窗”；
- 模板和 planner 按结果安排全幅段落（开场、情绪重句、结尾）；
- 提高 `headFill` 与窗口尺寸，用 `scripts/check_layout.mjs` 压测文字避让。

## 7 · 和传统剪辑技能的关系

传统剪辑技能的核心是做减法：粗剪、去停顿、去重复/卡壳、找 B-roll、铺 BGM。
本技能的核心是做包装：假定素材已干净连续，负责视觉系统、字幕、图形和节奏。

所以标准流水线是：**先粗剪干净 → 再用本技能包装**。原片有卡壳、重复、长停顿，本技能不会替你修；B-roll 也不是主线。

## 8 · 怎么选（速查）

- 要出成片、要人物主导 → `template/section` 或复制 `template/demo/tNN` 改；人物给全幅/大卡。
- 要短平快的强视觉段落 → 复制 `template/concepts/tNNN`，按 `references/concept-sections.md` 改。
- 要照抄已验收的实战结构 → `template/examples/`。
- 要让 Core 自动跑 → 用 `templates/` 的大写包，接受草稿级；不要把大写包当源码改。
- 没人物素材 → 只能用 `concepts/` 的 17 套 logo/text-only 配件（t83–t94、t96–t100），它们不是完整叙事模板。
